# Renderer rework, phase 1: the game's Direct3D usage

How Virtual-On Oratorio Tangram drives the Xbox 360 GPU, mapped from the recompiled code and
from call traces of a title-screen frame and a battle frame (Training, 2026-10-08). This is the
interface a native renderer has to implement. See `DEV_DIARY.md` section 5 for the overall
rendering picture.

## How it was measured

- The Xbox 360 Direct3D library is compiled into the game at `0x822BFE20`–`0x822E8000`
  (about 700 functions). Game code calls **147** of them directly.
- A temporary trace module (`src/d3d_trace.cpp`, generated by a script, not committed)
  hooked all 147 and recorded 30,000 consecutive calls with their first arguments (r3–r6, f1)
  and frame boundaries (Present). Recording starts on **F10** with
  `--d3d_trace_file=<path>`; analysis: `work/d3dtrace.py`.
- Each function was also checked for which GPU command packets its code can emit (draw,
  shader load, event/resolve, wait), via the call graph.

## Per-frame numbers

| | Title screen | Battle (Public Port) |
|---|---|---|
| Direct3D calls per frame | 4,412 | 11,345 |
| Distinct functions used per frame | 53 | 55 |
| API draw calls per frame | about 245 | about 450 |
| GPU draws per frame (emulator count) | about 460 | 1,150–1,350 |
| Resolves per frame | 35–37 | 42 |

GPU draws outnumber API draws because the main image is **drawn in tiles** (below): the
command stream is replayed once per tile.

The remaining ~91 functions are not called every frame: creation, loading and set-up (textures,
buffers, shaders, device).

## Key findings

1. **Predicated tiling.** The main 1280×720 frame (4× multisampled, 10-bit float HDR format)
   doesn't fit in the 360's 10 MB of on-chip memory, so the game renders it in **4 tiles**
   (tile masks `0x3`, `0x0C`, `0x30`, `0xC0`) and resolves each tile. A native renderer renders
   the frame once at any resolution and skips tiling entirely.
2. **Resolves are explicit and few.** One function (`sub_822CEF20`) does every resolve: a
   1024×1024 shadow map, the HDR downsampling chain (a loop of ~10, 1024 → 32 pixels), the
   tile resolves and the final image. Each becomes a native render-to-texture.
3. **Two draw paths.** Robots and stages use indexed triangle strips; full-screen passes and 2D
   use small immediate quads (BeginVertices / EndVertices).
4. **The device object** is at `0xA493ED80` (passed as the first argument to almost every call).

### Shaders and constants

| Function | Calls/frame | Arguments seen | Role | Confidence |
|---|---|---|---|---|
| `sub_822D2148` | 32 / 2156 | dev, 0 = vertex / 1 = pixel, first register, vec4 count | **GpuBeginShaderConstantF4**: writes a PM4 `SET_CONSTANT` header straight into the command buffer and returns the space for the caller to fill | high (code) |
| `sub_822C0460` | 484 / 1256 | dev, register, data, count | Set shader constants, marks per-register dirty bits | medium |
| `sub_822C02B0` | 1 / 6 | dev, 200, data, 16 | Set a 16-register constant block from register 200 | low |
| `sub_822C09E0` | 34 / 423 | dev, object pointer | Stores device+11824, dirty bit `0x80000`: likely SetVertexDeclaration | medium (code) |
| `sub_822C0808` | 12 / 37 | dev, vertex shader | **SetVertexShader** | high (code) |
| `sub_822C0648` | 12 / 76 | dev, pixel shader | **SetPixelShader** | high (code) |
| `sub_822C8A98`, `sub_822C8AE0` | 12 / 2 | dev, 0, number, surface | Both call `sub_822C9AD0` on the bound surfaces; role unclear | low |

**Shader binding.** `sub_822C0808` is **SetVertexShader** (device+12704) and `sub_822C0648` is
**SetPixelShader** (device+12700); both release the previous shader and set dirty flags. Besides
them, 16 game functions at `0x82583778`–`0x828621C0` write both fields directly (inlined
setters). At the next draw, `sub_822D7028` (the state flush every draw function calls) reads
both shaders and the vertex declaration (+11824) and sends the shader microcode with `IM_LOAD`.
A native renderer should hook the flush, not the setters: it sees every bind, inlined or not.
